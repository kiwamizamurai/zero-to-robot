# MuJoCo/Rerunの実務ガイド — なぜ・どうやって検算するか

01〜05は「フロムスクラッチ実装 → 数式証明」だったが、06はそもそも証明する数式がない。ここでやっているのは実務で必ず通る作業――**自分のロボットモデルを、信頼できる外部ツールと突き合わせて検算する**――そのものである。このページはTypstの証明ではなく、実際に手を動かすときに必要な知識をまとめた実践ガイドである。

## なぜMuJoCoで検算するのか

自作の順運動学・動力学の式が正しいかどうかを確認する方法は、大きく2つある。

1. **理論的に確認する**(01_kinematics・02_dynamicsでやったこと): 数式を手で導出し、Typstで証明する
2. **独立な実装と突き合わせる**(このフェーズでやること): 同じロボットを、自分のコードとは完全に別の実装(MuJoCo)で作り、同じ入力に対して同じ出力が出るか確認する

実務では(2)が特に重要になる。理由は単純で、**理論的な証明が正しくても、実装にバグがあれば動かない**からだ。逆に、実装だけ動いていても、それがたまたま特定のケースでしか合っていない可能性もある。MuJoCoのような「世界中の研究者・企業が何年も使い倒しているソフトウェア」と数値が一致すれば、自分の実装と理論の両方が同時に検証されたことになる。これは、機械学習で自作の勾配降下法の実装をscikit-learnの結果と突き合わせるのと全く同じ発想である。

産業界でも、新しいロボットの動力学モデルを実機に投入する前には、必ず何らかのシミュレータ(MuJoCo, Drake, PyBullet, Gazeboなど)で検証してから進める。「自分の式が合っている」という確信は、こうした独立な手段による裏付けなしには得られない。

## MuJoCoの基本: MJCFでロボットを定義する

MuJoCoはロボットの構造を**MJCF**(MuJoCo XML format)というXML形式で記述する。`01_mujoco_fk_jacobian.py`で使った2リンク平面アームの定義はこうなっている。

```xml
<mujoco>
  <option gravity="0 0 0"/>
  <worldbody>
    <body name="link1" pos="0 0 0">
      <joint name="joint1" type="hinge" axis="0 0 1"/>
      <geom type="capsule" fromto="0 0 0  1.0 0 0" size="0.02" mass="1.0"/>
      <body name="link2" pos="1.0 0 0">
        <joint name="joint2" type="hinge" axis="0 0 1"/>
        <geom type="capsule" fromto="0 0 0  0.8 0 0" size="0.02" mass="0.8"/>
        <site name="ee" pos="0.8 0 0"/>
      </body>
    </body>
  </worldbody>
</mujoco>
```

読み方のポイント:

- **`<body>`は入れ子で親子関係を表す**。`link2`は`link1`の内側に書かれているので、`link1`が動くと`link2`も一緒についてくる(ロボットアームの関節構造そのもの)
- `<body pos="...">`の`pos`は**親フレームから見た相対位置**である。`link2`の`pos="1.0 0 0"`は「`link1`の座標系で見て(1.0, 0, 0)」という意味で、これは`link1`の長さ`l1=1.0`だけ離れた場所に肘関節を置くことに対応する
- `<joint type="hinge" axis="0 0 1"/>`は「z軸まわりに回転する関節」。平面(xy平面)内の回転だけを扱いたいので、全ての関節軸をz軸に揃えている
- `<site>`は物理的な実体を持たない「印」で、手先位置のようにヤコビ行列や座標を取得したい場所に置く

この対応関係により、`01_kinematics/02_ik_gradient_descent.py`の`fk(q)`が計算する手先位置と、MuJoCoの`site`の位置が一致する。

## MuJoCoのAPI: 4つの関数とその役割

| 関数 | 何をするか | 対応する自作実装 |
|---|---|---|
| `mj_forward(model, data)` | `data.qpos`(関節角)から、全ての物体の位置・姿勢や各種物理量を計算する(順運動学+順動力学の下ごしらえ) | `fk(q)` |
| `mj_jacSite(model, data, jacp, jacr, site_id)` | 指定した`site`の並進(`jacp`)・回転(`jacr`)ヤコビ行列を計算する | `jac(q)` |
| `mj_fullM(model, data, dst)` | 疎行列で保持されている質量行列を、密行列`dst`に変換する | `mass_matrix(q)` |
| `mj_rne(model, data, flg_acc, result)` | Newton-Euler法の逆動力学。`flg_acc=1`なら`M(q)*qddot + c(q,qdot) + g(q)`、`flg_acc=0`なら`c(q,qdot) + g(q)`(加速度の寄与を除いた分)を返す | `inverse_dynamics(q,qdot,qddot)` / `coriolis_centrifugal(q,qdot)+gravity(q)` |

## 実際にハマった落とし穴

ドキュメントを読むだけでは気づきにくい、実装して初めて分かったことを3つ挙げる。

**1. `mj_forward`は`qacc`を上書きする。** `mj_rne`で逆動力学(`M*qddot+c+g`)を計算するには`data.qacc`に望みの角加速度を設定する必要があるが、その前に`mj_forward`を呼ぶと、`mj_forward`は順動力学(現在のトルクから生じる加速度)を計算して`data.qacc`を上書きしてしまう。正しい順序は「`qpos`・`qvel`を設定→`mj_forward`→その後で`qacc`を設定→`mj_rne`」である。ドキュメントの関数シグネチャだけを見ていると分からない、実行時の副作用である。

**2. バージョンによってデータ属性名が変わる。** 少し古い資料では質量行列の内部表現に`data.qM`という属性を使う例が見られるが、このセッションで使ったMuJoCo 3.14.0では`data.M`に名前が変わっていた。ライブラリのバージョンが違うと属性名やAPIが変わりうるので、`help()`や`dir()`で実際のバージョンの実物を確認してから使うのが確実(このリポジトリの各スクリプトも、この方法で確認しながら書いた)。

**3. 2D(平面)の問題を3Dエンジンで解く時は、余った自由度を「固定」ではなく「無視できる形」にする。** MuJoCoは本質的に3次元の物理エンジンなので、2リンク平面アームも実際には3次元空間に置かれている。今回は全ての関節軸をz軸に揃え、重力もxy平面内に設定することで、z軸方向の運動が一切発生しないようにした。慣性行列の対角成分(`diaginertia`)のうちz軸まわりの成分だけが結果に効き、x・y軸まわりの成分は(平面内运動にしか使わないので)どんな値でもよい。

## Rerunの基本: なぜmatplotlibではなくRerunなのか

`03_rerun_visualization.py`は、アームの動き(2Dアニメーション)と関節角・角速度の変化(時系列グラフ)を同時に可視化している。matplotlibでも似たようなことはできるが、違いは次の点にある。

- **matplotlib**: 静止画かGIF/動画ファイルを作る。後から「この時刻の値は何だったか」を数値で確認するのは難しい
- **Rerun**: 記録した`.rrd`ファイルをビューアで開くと、タイムラインをスクラブ(前後に動かす)しながら、3D/2Dの図形と時系列グラフが同期して動く。「アームがこの角度のとき、角速度は何だったか」をその場で確認できる

これはロボティクス・自動運転の実務でログを解析するときの標準的なワークフローに近い(実機やシミュレータの走行ログを、後から時系列で追いながら「あの瞬間に何が起きたか」を調べる)。

### Rerunの3つの概念

- **エンティティパス**(`"arm/link1"`のような文字列): データを識別する名前空間。ツリー構造で整理できる
- **アーキタイプ**(`rr.LineStrips2D`, `rr.Points2D`, `rr.Scalars`など): ログするデータの「型」。線分・点群・スカラー値の時系列など、目的に応じて使い分ける
- **タイムライン**(`rr.set_time("time", duration=t)`): 「いつのデータか」を指定する。同じタイムライン上に複数のエンティティをログすることで、ビューア上で同期して再生できる

### ハマった落とし穴: `rr.save()`はバッファリングされる

`rr.save(path)`を呼んだ直後にファイルサイズを確認すると、ログしたはずのデータに対して不自然に小さいことがある(このリポジトリでも、151フレーム分のデータを記録したのに最初は1.3KBしかなかった)。これはRerunがログを内部でバッチ処理してから書き出すためで、プロセスが終了する前に明示的に

```python
rr.get_global_data_recording().flush(timeout_sec=5.0)
```

を呼んでフラッシュする必要がある。スクリプトが正常終了しているのにファイルが小さい・データが欠けているように見えたら、まずこれを疑うとよい。
