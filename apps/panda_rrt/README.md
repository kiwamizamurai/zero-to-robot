# 障害物をよけて腕を動かす(Panda × MuJoCo の当たり判定 × RRT-Connect)

[ブラウザでシミュレーションを動かす](https://kiwamizamurai.github.io/zero-to-robot/panda_rrt/)

これまでのアームは「真上へ上がる → 横へ動く → 下りる」という、ぶつからないと分かっている道を人が決めていた。ここでは、腕の前に**高さ 60 cm の壁**があって、壁の向こう側へ手を移したい。どう動けばぶつからないかを、ロボット自身に探させる。

## このアプリで学べること

- **構成空間(C 空間)**: アームの姿勢は「7 つの関節角度」= 7 次元の空間の 1 点。壁にぶつかる姿勢は、その空間の中の「通れない領域」になる。道を探すのは、この 7 次元の空間の中
- **サンプリングによる経路計画(RRT)**: 7 次元をマス目に区切ると数が多すぎる。代わりに、ランダムに点を打って木を伸ばしていく
- **当たり判定は物理エンジンに聞く**: 「この姿勢でぶつかる？」を MuJoCo に毎回聞く。経路計画で一番時間がかかるのはここ
- **余裕(マージン)を取る**: 計画した道が壁すれすれだと、実行時のわずかなずれでかする。障害物を少し大きく見て計画する
- **道を後からなめらかにする**: RRT の道はジグザグなので、まっすぐつなげられる所は飛ばす(ショートカット)

**キーワード**: 経路計画(Motion Planning)、構成空間、RRT(Rapidly-exploring Random Tree)、RRT-Connect、サンプリングベース計画、衝突判定、ショートカット(平滑化)、マージン、OMPL、MoveIt、cuRobo

## 動かし方

**ブラウザ(おすすめ)**: [https://kiwamizamurai.github.io/zero-to-robot/panda_rrt/](https://kiwamizamurai.github.io/zero-to-robot/panda_rrt/)。手元で動かすときは、リポジトリのルートで `python3 -m http.server -d apps` を実行して、`http://localhost:8000/panda_rrt/` を開く(ES モジュールを読み込むので、ファイルを直接開く方法では動かない)。

**Python 版(元の実装)**: 次のとおり。

```bash
pip install -r apps/panda_rrt/requirements.txt
python apps/panda_rrt/rrt_plan.py            # 図と動画を output/ に
python apps/panda_rrt/rrt_plan.py --seed 3   # 乱数を変えると、見つかる道も変わる
```

## 何をしているか

1. **始まりと終わりの姿勢**: 手先の位置(青い玉 → 緑の玉)から、逆運動学(mink)で 7 つの関節角度を出す
2. **まっすぐ動かすと?**: 2 つの姿勢の関節角度を直線で補間すると、腕が壁を突き抜けてしまう。MuJoCo の当たり判定で分かる
3. **RRT-Connect で探す**: 始まりと終わりの両方から木を伸ばす
   - ランダムな姿勢を 1 つ選び、木の中で一番近い点から、その方向へ少しだけ(0.15 rad)枝を伸ばす
   - 伸ばした枝の途中で腕が壁や床にぶつからないかを、0.03 rad 刻みで MuJoCo に聞く
   - もう一方の木を、いま伸ばした点に向かって伸ばせるだけ伸ばす。2 つの木がつながったら道が見つかる
4. **ショートカット**: 道の途中の 2 点をまっすぐつなげても大丈夫なら、その間を飛ばす。これを 200 回試す
5. **実行**: 道に沿って 5 次多項式でなめらかに動かし、実際に壁や床に触れなかったかを数える

## 結果(`--seed 0`)

| 段階 | 結果 |
|---|---|
| まっすぐ補間 | 壁にぶつかる(実行すると 1361 ステップ壁に触れたまま止まる) |
| RRT-Connect | 260 回の試行で道が見つかった。かかった時間 0.32 秒(マシンによって変わる)、木の点 218 個、当たり判定 1264 回 |
| ショートカット | 経由点 57 → 7 個。関節空間での道のり 8.2 → 5.0 rad |
| 実行 | 壁や床との接触 **0 ステップ**。着いた位置のずれ 0.8 cm |

`--seed 1`、`--seed 2` でも、毎回違う道が見つかり、どれも接触 0 で着いた。

## 図の見方

- **左(手先の道すじを前から見たところ)**: 茶色が壁、赤い破線がまっすぐ補間した場合(前腕が壁に当たるので、手先は壁の手前で止まる)、青が RRT で見つけた道。手先は壁の上(60 cm)を越えて向こう側へ回り込んでいる
- **右(関節角度)**: 横軸がショートカット後の経由点、縦軸が 7 つの関節の角度。RRT は手先ではなく、この 7 つの角度の空間で道を探している。経由点の間はまっすぐ(各関節の角度を直線で補間)つないでいる

## 動画の要所(Python 版が書き出すもの)

動画と図は、Python 版のスクリプトを動かすと `output/` に書き出される(リポジトリが重くならないよう、コミットしていない)。ブラウザ版では、同じ様子を画面でそのまま見られる。

| コマ | 何をしているか |
|---|---|
| 左上・右上 | 関節角度をまっすぐ補間した場合。前腕(link5)が壁に当たって、それ以上進めない(手先は壁の 15 cm 手前で止まる) |
| 左下 | RRT の道。いったん手を上げ始める |
| 右下 | 壁の上を越えて、向こう側の緑の玉に着いた |

## 作ってみて分かったこと

- **計画した道でも、実行するとかすった**: 最初は、RRT で見つけた道で動かしても壁に 28 ステップ触れた。計画では壁すれすれでも通れる判定だったが、実際のモーターはわずかに遅れて動くので、かすってしまう。計画用には壁と床を 3 cm 大きく見る(当たり判定のマージン)ようにしたら、接触は 0 になった。実務でも、障害物を少しふくらませて計画するのが普通
- **当たり判定の数がそのまま計算時間**: 道を 1 本見つけるのに 1000 回以上当たり判定をしている。本物の計画ライブラリ(OMPL、MoveIt、GPU で並列に計算する cuRobo など)は、ここを速くする工夫を重ねている

## ブラウザ版と Python 版の違い

- 逆運動学は mink ではなく自前の減衰つき最小二乗法。乱数の列が違うので、同じ seed でも Python 版と同じ道にはならない。
- 枝の途中の当たり判定の刻みを、0.03 rad から 0.01 rad に細かくした。0.03 rad だと、壁をかすめる道が出ることがあったため。
- ブラウザ版の seed 0 の結果: 188 回の試行で道が見つかり(木の点 152 個、当たり判定 2518 回)、ショートカットで経由点が 46 → 5 個、道のりが 6.6 → 3.3 rad になった。まっすぐ補間は壁に 1361 ステップ触れ、RRT の道は接触 0 ステップで着いた位置のずれは 0.8 cm。
